### Vue d'ensemble

`angular-portfolio-app` est un **portfolio personnel front-only Angular 22** (zoneless, standalone, signals d'abord, Tailwind v4 CSS-first), **rendu en SSR avec prérendu SSG**. **Mode de rendu — fait structurant** : le build produit **5 routes prérendues** (`/`, `/about`, `/projects`, `/blog`, `/blog/:slug` avec `getPrerenderParams` qui interroge l'API de production au build) ; `login`, `two-factor` et `admin/**` sont en `RenderMode.Client`, et **tout le reste tombe sur le fallback `**` → `RenderMode.Client`** — ce qui inclut `/projects/:slug` (cf. F004). L'artefact vérifié porte 6 fichiers HTML avec `application/ld+json` et un `<title>` distinct par route. **Toute recommandation touchant `<head>` / `title` / `meta` / JSON-LD / cycle de vie à effet DOM doit préserver l'exécution serveur** — aucune API browser-only en remplacement.

L'organisation est une **Clean Architecture EAK stricte** : 9 features (`admin`, `analytics`, `auth`, `blog`, `contact`, `cv`, `home`, `profile`, `projects`) en 3 couches `domain`/`infra`/`application`, plus `core/`, `layout/`, `pages/`, `shared/`. **La discipline de typage et de template reste exemplaire et ne s'est pas érodée** : 0 `any`, 0 `interface`, 0 `*ngIf`/`*ngFor`, 0 `NgModule`, 0 décorateur `@Input`/`@Output`/`@ViewChild`, 0 `ngOnInit`/`ngAfterViewInit`, 0 cycle, 0 CVE, 0 barrel (acquis de 001). La dette réelle n'est pas dans le *style* du code : elle est dans **la tenue des invariants de rendu** (un ADR appliqué à moitié), **la sécurité du pipeline markdown**, et **une poignée de défauts mobile-first précis** — le reste des surfaces publiques est, contre toute attente, correctement responsive.

Sur l'axe **responsivité**, le sweep mécanique est largement rassurant : **aucune** largeur/hauteur fixe en px capable de déborder à 375 px, **une seule** grille sans variante mobile, **aucun** `h-screen`/`100vh` (le repo utilise `min-h-svh`, le bon choix face à la barre d'URL mobile), et les cibles tactiles de 44 px sont **systématisées par des tokens** (`icon-tile`, `admin-icon-btn`, `admin-pager-btn`, `button.ts:63` avec commentaire WCAG explicite). Les défauts restants sont ciblés : des liens textuels inline qui n'ont pas hérité de ces tokens, un paginator sans `flex-wrap`, et le zoom iOS sur le formulaire de contact.

Hotspots (volume × churn) : `home.ts` (43 commits), `app.config.ts` (40), `header.ts` (39, 240 LOC), `contact-form.ts` (34, 252 LOC), `admin-analytics.ts` (369 LOC), `admin-project-inline-form.ts` (341 LOC).

### Synthèse (≤ 10 points, classés par impact)

1. **F001** — Les 5 blocs `@defer` d'`/about` n'ont **aucun trigger régulier** : en navigation SPA (le chemin normal depuis le menu), 5 des 7 sections de la page restent bloquées sur leur `@placeholder` vide. Violation directe de la décision 4 d'ADR-0001.
2. **F002** — Le markdown des articles est injecté via `bypassSecurityTrustHtml` **sans aucun assainissement** : XSS stocké sur une page publique, figé jusque dans le HTML prérendu.
3. **F003** — `/projects/:slug` confond « liste vide » et « erreur API » : une panne backend produit un **skeleton perpétuel** annonçant « Chargement… » sans fin, sur une route déjà rendue côté client uniquement.
4. **F004** — `/projects/:slug` n'est pas prérendu alors que le sitemap **publie ces URLs** aux crawlers : les pages projet, cœur du portfolio, sont servies en coquille vide.
5. **F005** — La CSP de `index.html` (`script-src 'self'`, `frame-src 'none'`) **bloque Giscus** : la feature commentaires du blog est inopérante en production.
6. **F006** — `form-input` est en `text-sm` (14 px) : Safari iOS **zoome automatiquement** à chaque focus sur les 4 champs du formulaire de contact.
7. **F007** — Le bouton d'envoi du contact est `disabled` tant que le formulaire est invalide : l'utilisateur voit un bouton grisé **sans aucun message d'erreur**, et le `markAllAsTouched()` prévu pour ça est du code mort.
8. **F008** — L'environnement DOM des tests est `happy-dom`, **résolu transitivement et non déclaré**, alors que `package.json` déclare `jsdom` (jamais utilisé). Le régime de test dépend d'un aléa de résolution.
9. **F010** — Si l'API est indisponible au build, `getPrerenderParams` renvoie `[]` en silence : **zéro article prérendu, build vert**. Régression SEO invisible.
10. **F022** — Aucune CI : les 3 gates (414 tests, lint, build SSR) ne s'exécutent que sur le poste du développeur.

Preuve sur l'artefact : `dist/…/browser/blog/de-20-ans-de-metallurgie-a-developpeur-full-stack/index.html` fait 64 Ko et contient `<h1>`, un `<title>` propre et 1 bloc `application/ld+json` — le prérendu aboutit. Ne pas prescrire un `isPlatformBrowser` ici. _(La fragilité — la garde SSR repose sur un catch écrit pour du JSON malformé — relève du commentaire de conception, pas d'un finding actionnable.)_
- **`OnPush` explicite sur les 74 composants** — redondant en Angular 22, où `OnPush` est le défaut framework. **Ne pas le flagger** : c'est inoffensif, cohérent, et le supprimer sur 74 fichiers serait un diff massif à valeur nulle.
- **Reactive Forms sur 7 composants alors que Signal Forms est stable en v22** — motif que la grille invite à signaler sur du **neuf**. Vérification faite, ces formulaires ne sont pas neufs : `contact-form.ts` date du 2026-02-07 (commit `2d95542`), antérieur de plusieurs mois à la migration v22 du 2026-06-25. Ce n'est pas une incohérence de conception mais un legacy non migré ⇒ **question ouverte, pas finding**.
- **`proxy.conf.cjs` signalé « unused file » par knip** — référencé par `angular.json:70` (`"proxyConfig": "proxy.conf.cjs"`), consommation de configuration invisible aux outils statiques. Conserver.
- **`@fortawesome/fontawesome-free`, `@sentry/cli`, `lint-staged` signalés « unused devDependencies »** — consommés respectivement par `scripts/build-icons.mjs` (chemin filesystem vers `node_modules/@fortawesome/…/svgs`), le script `sentry:sourcemaps`, et la config `lint-staged` du `package.json`. Faux positifs déjà établis en 001, reconfirmés. Ne pas retirer. _(En revanche `eslint-plugin-prettier`, signalé dans le même lot, est un **vrai** positif — cf. F025 : la config n'importe que `eslint-config-prettier`.)_
- **`depcheck` « Missing dependencies » : `@core/*`, `@shared/*`, `@features/*`, `@layout/*`** — ce sont les alias de chemins TypeScript (`tsconfig` `paths`), pas des paquets npm. Faux positif intégral, aucune action.
- **`two-factor-enable-form.ts:61` et `file-dropzone.ts:35` : `<img [src]>` brut au lieu de `[ngSrc]`** — `NgOptimizedImage` **refuse par conception** les data URIs et les blob URLs. Le premier rend un QR code en data URI, le second un aperçu de fichier local. Exceptions légitimes, pas des oublis.
- **`@apply` massif dans les blocs `@utility` de `styles.css`** — CLAUDE.md écrit « réutilisation = composant Angular, pas `@apply` ». Mais le profil-projet autorise explicitement la config CSS-first en `@theme`/`@utility` de `src/styles.css`, et `@utility` est le mécanisme d'extension sanctionné de Tailwind v4. Non flaggé ⇒ la tension de doctrine est portée en question ouverte, pas en finding.
- **`InMemoryProfileGateway` / `InMemoryHomeGateway` câblés en production (`app.config.ts:171`, `:174`)** — ressemblent à des fakes de test fuités ; ce sont l'implémentation runtime légitime des features `profile`/`home`, actée par le profil-projet. Leurs specs dédiés ne sont pas rejetés. Inchangé depuis 001.
- **`app.routes.server.ts:25` remonté par le grep d'archéologie** — le pattern `/\*\*` matche le glob de route `{ path: 'admin/**', … }`, pas un commentaire. Hit mécanique sans jugement, correctement classé sans suite (mentionné dans F024 pour la traçabilité).

### Questions ouvertes pour l'équipe

- **Signal Forms** : le repo est en v22, `@angular/forms/signals` est stable, et **zéro import** n'existe dans `src/`. Les 7 formulaires en Reactive Forms sont antérieurs à la migration. Doctrine à fixer : tout **nouveau** formulaire en Signal Forms (et migration opportuniste), ou gel assumé sur Reactive Forms tant que rien ne le force ? La réponse doit descendre dans le profil-projet, sinon chaque agent AAK tranchera différemment.
- **CI (F022)** : elle a été retirée volontairement en juin 2026 ; le repo a depuis gagné une feature entière, 144 tests et 19 fichiers. Le hook pré-commit local (contournable, et qui ne lance ni lint ni build) est-il toujours un filet suffisant, ou la réintroduction d'un workflow `verify` unique se justifie-t-elle maintenant ?
- **Giscus (F005)** : la CSP le bloque, et `giscus-config.ts:14-17` indique que l'installation de l'app GitHub restait « une étape manuelle » possiblement jamais faite. La feature commentaires est-elle un objectif tenu ou du code à retirer ? Tant que la question n'est pas tranchée, `blog-comments.ts` est du code mort qui pollue aussi la sortie de test (F015).
- **`@apply` dans `@utility`** : CLAUDE.md l'interdit, le profil-projet autorise la config CSS-first Tailwind v4 dans `styles.css`. Les deux documents se contredisent sur ~15 utilitaires. Lequel fait foi ? (Recommandation : préciser dans CLAUDE.md que l'interdiction vise les classes CSS custom ad hoc, pas les `@utility` du design system.)
  → **Tranché le 2026-09-08, ADR-0003** : `@utility` légitime pour un élément natif unique non enveloppable, `@apply` uniquement dans ces blocs de `styles.css`, composant pour toute structure multi-éléments. CLAUDE.md et le profil alignés ; les 20 utilities existantes sont conformes.
- **Result pattern** : prescrit par CLAUDE.md pour les erreurs métier, toujours employé dans le seul `http-contact.gateway.ts`. Les autres gateways propagent l'erreur RxJS ou l'avalent en `of([])` (cause racine de F003 et F030). Généraliser ou assouplir la doctrine ?
- **Règle ESLint `explicit-function-return-type`** (posée en 001, jamais tranchée) : la réérosion observée en F029 sur la feature la plus récente suggère que le statut `warning` ne tient pas dans la durée. La hausser en `error` sur `src/**` ?
